# M4.1 — TokANSH 1.0/1 → 1.1/2 upgrade runbook

**Review status:** implementation/offline validation only. No phase has been run
against DRUNIX by this change. Obtain independent review and explicit operator
authorization for each phase and organization. Acknowledgement flags record intent;
they are not authentication. **Option B desired-state approval is implemented for
offline review, not authorized for live execution by this change.** The generic
approval phase flag remains inspection-only. Submission also requires a separately
reviewed organization-specific replacement/repair acknowledgement, described below.
No approval absence is established. Do not use the initial-deployment script for
this upgrade.

## Fixed scope and trust boundaries

Target: `mychannel`, `tokansh`, version `1.1`, sequence `2`,
`AND('Org1MSP.peer','Org2MSP.peer')`, escc/vscc, no init, no collections. The current
committed definition must be exactly 1.0/1 before mutations. An unexpected version,
sequence, plugin, policy, collection or init setting stops the phase. A target
already committed cannot be recommitted; use `verify` for full post-upgrade acceptance.
The policy check requires the reviewed ApplicationPolicy protobuf bytes from the
existing tooling; a different but equivalent serialization conservatively stops.

Only Lite Peers install the package (Org1 7051, Org2 9051). Lifecycle approval,
readiness and commit use Committing Peers (7061, 9061), each with its own Admin MSP.
Both CPs and both LPs must report the same all-definitions response. Named
`querycommitted --name` output is deliberately not used: it omits the name.
Read-only application calls to either LP use the **existing Org1 User1** identity,
because `GetOperation` requires the pinned registration authority, including when
querying Org2. No keys are copied, generated, read by Python, or printed. The peer
CLI loads the existing MSP for each explicitly scoped child process.

Paths under `NETWORK_ROOT/drunix-network/test-network/organizations/`:

- Admin MSP: `peerOrganizations/orgN.example.com/users/Admin@orgN.example.com/msp`.
- Application MSP: `peerOrganizations/org1.example.com/users/User1@org1.example.com/msp`.
- Peer TLS CA: `peerOrganizations/orgN.example.com/peers/peer0.orgN.example.com/tls/ca.crt`.
- CP TLS pin/certificate: `peerOrganizations/orgN.example.com/peers/peer1.orgN.example.com/tls/server.crt`.
- Orderer CA: `ordererOrganizations/example.com/orderers/orderer.example.com/tls/ca.crt`.

Single-peer calls select `peer0.orgN.example.com` or `peer1.orgN.example.com` as
appropriate. The multi-CP commit clears the shared hostname override: each actual
CP certificate must validate **localhost** and its own organization CA. Static
`openssl` checks precede that call; the CLI verifies TLS during connection.
Orderer: `localhost:7050`, TLS name `orderer.example.com`, explicit orderer CA.
The workflow does not rewrite certificates or downgrade TLS to make this work.
The source-reviewed shared override is in DRUNIX
`internal/peer/lifecycle/chaincode/client_connections.go:89–94`, which creates each
connection through the common peer client configuration.

The accepted Org2 Writers policy exception is **isolated local hackathon only**.
It is not authorization for shared, cloud or production operation. Policies remain
unchanged. Binding uses trusted local paths, CP certificate DER hashes, channel
name, unique deployment ID and reviewed file hashes. It is not cryptographic
channel/genesis identity anchoring or live certificate fingerprint pinning.
Filesystem integrity, baseline freshness and an exclusive operator window remain
operator responsibilities. Do not copy a context to a different environment,
relabel an old baseline, or delete attempt markers to bypass a stop.

No historical package identity is selected automatically. The accepted M3 package
record and deployment helpers remain unchanged and cannot authorize 1.1/2.

The runner performs two separate local commands of this form:
`peer lifecycle chaincode package <archive> --path <staged-chaincode> --lang golang

and cached toolchain, not all machines/toolchains or arbitrary source paths.
All commands have bounded timeouts. Ordinary unit tests (command 006) and race

Partial outputs are retained; do not retry over
them or overwrite them. Review failure evidence and choose a new release directory
only after independent review. No install follows packaging automatically.

## Independent lifecycle checkpoints

Run **one line only** after that phase's explicit authorization. Never chain lines
into a script or loop. Every phase revalidates the context/package, local CP pins,
current definitions, contract metadata and property/receipt/basic preservation.
An advisory lock excludes simultaneous phases using this release directory.

```bash
# Phase 3: Org1 LP install; MATCH skips, validated ABSENT permits one attempt.
bash scripts/drunix/upgrade-proposed.sh install-org1 --authorize-install-org1 "${CONTEXT_ARGS[@]}"
# Phase 4: separately authorized Org2 LP install.
bash scripts/drunix/upgrade-proposed.sh install-org2 --authorize-install-org2 "${CONTEXT_ARGS[@]}"
# Phase 5: Org1 CP approval INSPECTION ONLY without the additional acknowledgement.
bash scripts/drunix/upgrade-proposed.sh approve-org1 --authorize-approve-org1 "${CONTEXT_ARGS[@]}"
# Phase 6: Org2 CP approval INSPECTION ONLY without the additional acknowledgement.
bash scripts/drunix/upgrade-proposed.sh approve-org2 --authorize-approve-org2 "${CONTEXT_ARGS[@]}"
# Independent read-only approval verification; invoke separately for each org.
bash scripts/drunix/upgrade-proposed.sh verify-approval-org1 --authorize-verify-approval-org1 "${CONTEXT_ARGS[@]}"
bash scripts/drunix/upgrade-proposed.sh verify-approval-org2 --authorize-verify-approval-org2 "${CONTEXT_ARGS[@]}"
# Phase 7: independently authorized readiness, after reviewing both MATCH records.
bash scripts/drunix/upgrade-proposed.sh readiness --authorize-readiness "${CONTEXT_ARGS[@]}"
# Phase 8: one commit attempt, only with both reviewed sequence-2 approvals.
bash scripts/drunix/upgrade-proposed.sh commit --authorize-commit "${CONTEXT_ARGS[@]}"
# Phase 9: separately authorized read-only verification.
bash scripts/drunix/upgrade-proposed.sh verify --authorize-verify "${CONTEXT_ARGS[@]}"
```

Installation uses strict MATCH / validated ABSENT / CONFLICT / INVALID parsing from
the existing helper. Only validated ABSENT can authorize install. Duplicate package
IDs/labels, duplicate keys, malformed JSON or missing fields stop. A matching label
with another hash is a conflict. Commit requires exact installed packages and exact
sequence-2 approvals (including package source), latest independent MATCH verification records, and readiness true for both MSPs.
It repeats both-org preservation checks just before the single commit call. No
unexpected committed definition is accepted as an absence or a reason to upgrade.
No installation, approval or commit invocation automatically advances to another phase.

Before any lifecycle mutation a durable owner-only `attempt-<phase>.json` with
UNKNOWN outcome is exclusively created and fsynced (file and directory). Existing
attempt records block another mutation attempt, including after process crash.
A returned CLI success adds a separate `acknowledged-<phase>.json`; it is **not**
proof of deployment. Nonzero exit, timeout, process failure or lost response is
UNKNOWN and leaves the marker intact. There are no retries, automatic removal,
re-approval, recommit, rollback, teardown or service/container restart commands.
The mutex/markers are local operational safeguards, not global exactly-once delivery.
Another operator with credentials can bypass them; local filesystem control is trusted.

Post-upgrade verification requires both LPs/CPs to agree on 1.1/2 and the exact
policy/plugins/no-init/no-collections, both packages installed, both exact approvals,
unchanged full property/registration receipt/basic state and the eight M4.1 metadata
functions. No `IssueANSH`, registration, prepare, submit or commit-status call occurs.
Successful lifecycle verification does not prove business issuance works on-chain.

## Approval ambiguity — confirmed source findings

Inspected in the local DRUNIX source (no live queries):

- `internal/peer/lifecycle/chaincode/queryapproved.go:136–141`: unsuccessful proposal
  response becomes a generic nonzero CLI error before JSON printing.
- `core/chaincode/lifecycle/lifecycle.go:551–552`: missing private namespace
  parameter metadata produces `could not fetch approved chaincode definition`.
- Same file `:570–571`: parameters exist but local package-source metadata is
  missing; the **same error** is returned. Exact text cannot distinguish absence.
- `core/chaincode/lifecycle/scc.go:422–452`: the supported query dispatch calls
  that same function and returns parameters and source together. An SDK/protobuf
  call to it inherits the ambiguity; JSON decoding cannot repair it.
- `core/chaincode/lifecycle/lifecycle.go:646–660`, `serializer.go:249–252`:
  readiness compares serialized parameter hashes. A false result can indicate
  missing **or different** parameters; it does not establish no approval or prove
  package-source completeness. True also does not replace package-source checking.
- `core/chaincode/lifecycle/scc.go:600–635`: all-definitions enumerates public
  committed definitions, not private per-org approval state. A missing sequence 2
  there does not prove absence of an uncommitted approval.
- The pinned CLI command set has no query-all-approved path. Reading private DB
  internals or inferring from historical blocks would add an unreviewed trust/
  completeness assumption and is not implemented.

The ambiguity remains unresolved as an **absence** signal. Option B instead
changes the authorized action: establish exactly the reviewed approval, including
possible replacement/repair of uncommitted sequence-2 state. It does not reinterpret
an unsuccessful query as absence and does not use readiness=false as authorization.

The native source permits replacing different uncommitted parameters/package
associations (`lifecycle.go:463–509`) and rejects an unchanged uncommitted approval
(`:489–490`). Some malformed states cannot be repaired by native approval; failure
stops without retries. `approveformyorg.go:233–240` sets DRUNIX's APPROVE envelope type,
broadcasts through its native CLI and waits for the selected peer event. The event
handler rejects non-VALID outcomes (`internal/peer/chaincode/common.go:823–829`).
No generic Fabric transaction submission replacement is used.

### Organization-specific desired-state approval

The exact operator checkpoints are independent actions in this order. Read the
complete runbook first; do not concatenate these checkpoints into automation.

| Checkpoint | Action | Required stop/review before proceeding |
|---|---|---|
| A | Prepare/review package locally | Review reproducibility and package identity |
| B | Read-only preflight and freeze context | Review M3 records, pins, hashes and maintenance plan |
| C/D | Separately install Org1/Org2 packages | Inspect each result; uncertain mutation stops |
| E | One desired-state Org1 approval attempt | Stop at acknowledgement or UNKNOWN; no verification chaining |
| F | Independently verify Org1 approval | Review latest MATCH and original-transaction evidence limitation |
| G | One separately authorized desired-state Org2 approval attempt | Org1 must already have independent MATCH verification if its attempt marker exists |
| H | Independently verify Org2 approval | Review latest MATCH and all preservation checks |
| I | Separately authorize readiness | Both latest MATCH records must agree with fresh approval reads |
| J | Separately authorize definition commit | Preserve the existing two-org/preservation/one-attempt guards |
| K | Separately verify upgraded definition | Full post-upgrade checks; no ANSH issuance |

Only use this path after explicit human authorization for **one** organization.
The authorization includes creating, replacing or repairing prospective sequence-2
approval; it does not authorize changing the current committed definition, another
organization's approval, the endorsement policy, application records or token supply.
A visible differing approval is recorded before the operator-authorized replacement.

Create a separate owner-only external authorization file for the requested
organization, directly under the reviewed release directory. Use
`desired-state-approval.example.json` as a **non-executable template**; replace its
package ID, deployment ID and context SHA-256 from the independently reviewed
context. Org1 uses `organization: Org1MSP`; Org2 requires a separately reviewed file
with `organization: Org2MSP`. Do not generate both authorizations in an unattended
loop. The file contains only these exact fields:

- `schema_version`: integer 2 (older unreviewed prototype files are rejected).
- `organization`, `channel`, `chaincode`, `version`, `sequence`, `package_id`.
- `context_sha256`, `deployment_id`.
- `acknowledgement`: the exact replacement/repair sentence below.
- `maintenance_acknowledgement`: the exact maintenance-window sentence below.

All values must exactly match the phase and reviewed context. The full context
continues to bind package bytes/SHA-256, baseline, source identity, pins and lifecycle
configuration. No upgrade-context schema or frozen context needs changing for this
new gate. Unknown/duplicate/missing JSON fields, incorrect types, a wrong organization
or hash, and partial/repeated/abbreviated CLI options are rejected. A file must be
operator-owned, mode 600, and stored outside both source repositories. Review and
record its SHA-256 separately; it is not inferred from the context automatically.
An operator-controlled maintenance window with **no competing lifecycle operators
and no known in-flight conflicting lifecycle operations** is mandatory. Confirm it
out of band across both organizations and all release directories. The release-local
file lock excludes only cooperating processes using that directory; it cannot
establish exclusive control of the network. A known commit-attempt marker blocks
approval. Another organization's local approval-attempt marker requires independent
MATCH verification and a fresh exact approval read before another approval attempt.
These checks do not discover other operators or pending orderer transactions. Do
not acknowledge a maintenance window unless the operator has established it.

The file and flags are local operator attestations, not bearer secrets or signatures;
existing organization Admin MSP signing and verified TLS remain the actual network
authentication boundary.

installed on that organization's LP; unchanged package hash; the corresponding

### Independently invoked post-approval verification and recovery

After reviewing the mutation result, independently authorize the selected read-only
phase. It uses the correct Admin/CP, reads exact sequence 2 and rechecks both-org
public 1.0/1 definitions, relevant LP agreement, registered property/receipt and
basic assets against the frozen baseline. Heights/hashes must agree and remain
stable during this read-only observation; height need not equal the older baseline.
It records one of:

| State | Meaning | Progression |
|---|---|---|
| MATCH | Exact version, sequence, package and all reviewed lifecycle parameters | Eligible only after operator review and separately authorized readiness |
| CONFLICT | A different complete approval was observed | Stop; no implicit replacement/retry |
| INCOMPLETE | Supported indication that reviewed approval is incomplete, currently native unavailable package source | Stop; only a first separately authorized desired-state attempt may repair it |
| UNKNOWN | Ambiguous missing-component error, malformed output, timeout or insufficient evidence | Stop for independent/manual investigation |

Each invocation appends a private immutable
`approval-verification-orgN-00000001.json` (increasing sequence numbers); old evidence
is never replaced. Failed inspections append UNKNOWN, so an older MATCH cannot be
silently reused. Every record binds organization, target definition/package,
reviewed context hash and deployment ID, plus the observed approval, channel state,
preservation result and available local intent/acknowledgement evidence.

```bash
  --authorize-verify-approval-org1 "${CONTEXT_ARGS[@]}"
```


Review each record before any progression. Readiness/commit require both organizations'
latest records to be MATCH in this exact context and agree with fresh exact approval
queries. A record at an unchanged height must have matching hashes; a record ahead
of the current chain is rejected. A new UNKNOWN/CONFLICT/INCOMPLETE record blocks
progress even if an older MATCH exists. Current M3 preservation checks still run.

The verification standard for this **isolated local MVP** is independently observed
exact desired approval state plus verified preservation. It establishes that the
required approval exists; it does **not** establish which original attempt committed.
The tool checks available local intent and native acknowledgement records, their
hashes/bindings and private diagnostic directory references. It deliberately reports
`original_attempt.transaction_validation: UNKNOWN`; it never infers COMMITTED_VALID
from an exact state match, process exit or log text. No transaction ID is fabricated.
The CLI does not persist a transaction ID before broadcasting here. Early interruption
can leave it unavailable. Genuine original transaction/validation evidence must be
recovered and reviewed separately where available; this workflow does not automate
that correlation. If original-transaction proof is required by governance, remain
NO-GO until it is obtained; state-only acceptance is not a production control.

For UNKNOWN recovery: retain the attempt marker; separately invoke verification;
review its new record; only after MATCH and acceptance of this explicit state-based
standard may the operator authorize readiness. This independent inspection followed
by a separately authorized readiness decision is the recovery/progression checkpoint,
not a retry decision. A repeated approve invocation may inspect a matching state
without submission, but creates no verification record and cannot satisfy the gate.
Conflicting/incomplete/unknown observations stop. Do not delete/reset markers,
create a new release to bypass them, or interpret unchanged-content errors as commit
evidence. There is no force, reset, ignore-unknown or retry option.

Local file ownership, plain acknowledgement flags and a maintenance-window assertion
are insufficient production governance. Shared/cloud/production operation needs
reviewed network-wide coordination, stronger operator authorization/audit controls
and the existing Org2 policy exception resolved separately. This procedure grants
no approval for those environments.

## STOP, recovery and evidence

Stop for any hash/pin/identity/policy mismatch, CP/LP disagreement, preservation
failure, unexpected channel change, unrecognized query/CLI error, missing dependency, lock
contention, malformed lifecycle state or prior attempt marker. A conflicting target
approval permits only its first explicitly reviewed desired-state replacement;
without that authorization, stop. Conflicts in committed definitions always stop.
Secure the release directory; do not retry a mutation or reset the network. Request
separate read-only inspection of installed package IDs, exact per-org approval and
both committed definitions. Existing matching install can be inspected without
mutation. Use `verify` only after separately authorized approval of its reads.
If a prior commit is found valid, verification may pass while the old UNKNOWN intent
remains as historical evidence. Never delete the marker to repeat a lifecycle action.
If effect cannot be established, retain UNKNOWN and escalate; there is no automated
recovery or rollback. A corrective change would be a separately reviewed later
sequence, never a ledger restore or deletion.

Raw command stdout/stderr is written only under private `upgrade-evidence-*`
directories. Terminal messages are sanitized. Do not publish raw peer logs, keys,
certificates containing private material, databases, prepared/signed artifacts,
chaincode archives or evidence in Git. Retain package, reviewed context/baseline,
source identity and attempt records beyond temporary-directory cleanup. Share only
reviewed nonsecret hashes/IDs and sanitized result summaries. Do not alter an
artifact to sanitize it; create a separate reviewed summary.

Remaining runtime gates: peer lifecycle compatibility is source-derived until
this separate upgrade is authorized; read propagation may be delayed and fails
without polling/retry. Local file checks cannot prove channel continuity against
a reset retaining credentials. Gateway contract-info parsing still expects M3's
four functions, so deploying M4 would require a separately reviewed Gateway
compatibility change before claiming full application readiness. Cold namespace
latency and five-second evaluation deadlines remain risks for later issuance
acceptance; `/ready` and connected business workflows are not enabled here.
